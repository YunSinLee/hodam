# 8쪽 그림책 베타 운영 기준

정식 출시 전 기준은 새로 만드는 8쪽 그림책이다. 공개 검색 페이지는 계속 운영하고, 첫 이용자가 그림책을 완성하고 다시 읽는 경험을 우선 검증한다.

## 책장과 기존 기록

- `/my-story`는 새 그림책을 기본으로 보여준다. 첫 4쪽은 결말을 고를 수 있고, 결말까지 저장하면 8쪽으로 표시한다. 본문 완성과 삽화 준비는 별도이므로 목록의 상태는 `8쪽 · 결말 완성`으로 표기한다.
- `/my-story/archive`는 기존 동화와 내용 확인이 필요한 기록을 보관한다. 원문, 영어, 그림, 소유권을 바꾸거나 8쪽으로 자동 변환하지 않는다.
- 분류는 저장된 원고가 그림책 형식으로 해석되는지를 기준으로 한다. 생성일이나 `openai_thread_id` 접두어로 나누지 않는다. 보관함에서는 읽을 수 있는 동화를 먼저 보여주고, 글이 없는 기록 등은 `내용 확인이 필요한 기록` 필터로 확인한다.
- 예전 기록이 있는 계정에는 기본 책장에서 보관함 링크와 기록 수를 표시한다. 예전 동화를 읽고 돌아오면 보관함으로 이동한다.
- 보관함도 개인 페이지다. 인증·소유권 보호와 검색 제외를 유지한다.
- 2026-09-14 확인 시 예전 형식 기록 706건이 9개 계정에 걸쳐 있었고 테스트 계정 표시가 없었다. 테스트용이라고 단정할 수 없어 삭제하지 않았다. 이 수치는 `openai_thread_id` 접두어를 기준으로 한 보존 대상 조사이며, 완성된 동화 수가 아니다.

## 출시 전 확인할 흐름

1. 로그인 전 작성한 입력이 로그인 후에도 유지된다.
2. 첫 계정의 프로필·곶감·빈 책장이 준비된다.
3. 첫 4쪽이 검수를 통과한 뒤 저장되고 곶감은 한 번만 사용된다.
4. 첫 4쪽을 읽고 세 가지 행동 중 하나를 고르면 결말 4쪽으로 이어진다.
5. 8쪽 글과 삽화 8장을 확인한다. 누락된 삽화는 기존 글과 이미지를 보존하며 다시 요청할 수 있다.
6. 책장을 떠났다가 돌아와도 내용·선택한 결말·그림이 유지된다.
7. 예전 동화는 보관함에서 원문 그대로 읽고, 새 그림책과 혼동하지 않는다.

원고 검수에 실패한 글은 저장하지 않는다. 실패율과 재시도 성공률은 베타 점검 항목이다. 한 번의 성공을 모든 입력에 대한 품질 보증으로 취급하지 않는다.

새 실패 로그 `picturebook_generation_failed`는 시작·결말 단계와 모델 연결·시간 초과·응답 형식 등 고정된 분류만 남긴다. 원고·입력·공급자 오류 본문은 기록하지 않는다. 이미 처리된 `GenerationError`는 이 로그를 남기지 않으므로, 이 로그 건수만으로 전체 품질 거절률이나 사용자 재시도 성공률을 계산하지 않는다.

## 테스트 데이터

새 운영 QA 계정에는 `hodam_test_user: true`와 용도를 표시하고 가상의 아이 정보를 사용한다. 테스트용 원고·빈 기록도 해당 계정에만 만든다. 실제 사용자 기록은 QA 목적으로 변환하거나 삭제하지 않는다.

OAuth 제공자의 신규 가입, 앱의 첫 계정 초기화, 원고 생성, 결말 생성, 삽화 생성, 재방문 검증은 각각 기록한다. 관리자 API로 준비한 테스트 계정의 로그인 검증을 Google·카카오 신규 가입 완료로 기록하지 않는다.

### 의존성 점검

- 배포 전 검사에서 발견한 `brace-expansion`, `fast-uri`, `source-map-js` 경고는 호환 패치 버전으로 업데이트했다. Sass는 1.105.1로 올려 오래된 Chokidar·braces 경로를 제거했다.
- `sass`와 `next-sitemap`은 SCSS 컴파일과 `postbuild` 사이트맵 생성에만 사용하므로 개발 의존성으로 분류했다. CI·Vercel 빌드 단계에서는 개발 의존성까지 설치해야 한다. `npm run check:audit:prod` 결과는 경고 0개다.
- 개발 도구를 포함한 전체 `npm audit`에는 18개 경고(높음 16개, 보통 2개)가 남아 있다. 이 숫자는 두 원인 패키지와 그 상위 의존성 경고를 합친 수다. [braces의 중첩 패턴 재귀 문제](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)는 수정 버전이 아직 없고, [PostCSS 선택자 파싱 문제](https://github.com/advisories/GHSA-rj75-hqrm-r3gf)는 Tailwind 3의 하위 의존성에 남는다. 현재 사용 경로는 저장소에 정의한 파일 패턴·CSS를 처리하는 빌드·린트 도구이며 서비스 이용자의 입력을 이 파서에 넘기지 않는다. 전체 검사가 통과했다고 기록하지 않는다.
- 해결되지 않은 도구 경고는 상위 패키지의 호환 수정판 또는 별도 Tailwind·린트 도구 업그레이드에서 재검토한다. 전체 검사 결과는 `reports/local/mobile-qa-2026-10-06/dependency-audit.json`에 저장한다.

### 운영 로그인 후 복귀 보완

0.2.3 배포 확인 중 운영 Google 기존 계정으로 책 상세에서 로그인을 시작했을 때, 인증 응답이 `/auth/callback` 대신 홈의 `?code=...`로 도착하는 경우를 확인했다. SDK가 로그인과 코드 제거를 완료하지만 홈에는 저장된 복귀 경로를 처리하는 로직이 없어 원래 책으로 돌아가지 않았다. 운영 Supabase의 반환 주소 허용 목록은 관리자 재로그인이 필요해 확인하지 못했으므로 외부 설정 원인으로 단정하지 않는다.

0.2.4는 홈의 GET 요청에 인증 코드 또는 오류 응답이 있는 경우 같은 출처의 `/auth/callback`으로 307 이동한다. 쿼리를 보존하고 SDK 초기화 전에 기존 콜백 처리로 연결한다. 일반 홈·다른 경로·POST 요청은 그대로 두며, `next` 값으로 목적지를 변경하지 않는다. 기존 콜백의 세션 검증·안전한 복귀 경로 처리·오류 안내를 재사용한다. API의 요청 ID 전달도 유지한다.

추가 회귀 테스트 13개를 포함한 전체 191개 파일·1,276개 테스트, 프로덕션 빌드와 변경 파일 린트가 통과했다. 독립 코드 검토에서 추가 결함은 없었다. 실제 운영 재로그인 결과는 배포 후 확인한다.

실제 로컬 HTTP 검사에서 루트의 `middleware.ts`가 `src/app` 구조에서는 빌드에 포함되지 않는 것을 확인했다(`middleware-manifest.json`이 비어 있음). 파일을 앱과 같은 레벨인 `src/middleware.ts`로 옮겼다. 최종 빌드에서 미들웨어 등록과 코드·오류 응답의 실제 307 이동, 일반 홈 200, 비인증 API 401 및 요청 ID 전달을 검증했다. 함수 단위 테스트만으로 배포 경로 검증을 대신하지 않는다.
