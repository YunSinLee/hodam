# 8쪽 그림책 베타 운영 기준

정식 출시 전 기준은 새로 만드는 8쪽 그림책이다. 공개 검색 페이지는 계속 운영하고, 첫 이용자가 그림책을 완성하고 다시 읽는 경험을 우선 검증한다.

## 책장과 기존 기록

- `/my-story`는 새 그림책을 기본으로 보여준다. 첫 4쪽은 결말을 고를 수 있고, 결말까지 저장하면 `8쪽 · 이야기 완성`으로 표시한다. 본문 완성과 삽화 준비는 별도이므로 `그림 4/8장`처럼 삽화 수도 함께 표시한다. 저장소 조회에 실패하면 글은 계속 열 수 있고 그림은 책에서 확인하도록 안내한다.
- 새 그림책의 첫 쪽 삽화를 책장 표지로 표시하며, 그림이 없으면 제목·아이 이름이 있는 표지를 사용한다. 읽기 마지막 쪽에서도 글만 완성된 상태와 삽화까지 완성된 상태를 구분한다. `이야기 글 저장 (.txt)`에는 삽화를 포함하지 않는다.
- `/my-story/archive`는 기존 동화와 내용 확인이 필요한 기록을 보관한다. 원문, 영어, 그림, 소유권을 바꾸거나 8쪽으로 자동 변환하지 않는다.
- 분류는 저장된 원고가 그림책 형식으로 해석되는지를 기준으로 한다. 생성일이나 `openai_thread_id` 접두어로 나누지 않는다. 보관함에서는 읽을 수 있는 동화를 먼저 보여주고, 글이 없는 기록 등은 `내용 확인이 필요한 기록` 필터로 확인한다.
- 예전 기록이 있는 계정에는 기본 책장에서 보관함 링크와 기록 수를 표시한다. 예전 동화를 읽고 돌아오면 보관함으로 이동한다.
- 보관함도 개인 페이지다. 인증·소유권 보호와 검색 제외를 유지한다.
- 2026-09-14 확인 시 예전 형식 기록 706건이 9개 계정에 걸쳐 있었고 테스트 계정 표시가 없었다. 테스트용이라고 단정할 수 없어 삭제하지 않았다. 이 수치는 `openai_thread_id` 접두어를 기준으로 한 보존 대상 조사이며, 완성된 동화 수가 아니다.

## 출시 전 확인할 흐름

1. 로그인 전 작성한 입력이 로그인 후에도 유지된다.
2. 첫 계정의 프로필·곶감·빈 책장이 준비된다.
3. 첫 4쪽이 검수를 통과한 뒤 저장되고 곶감은 한 번만 사용된다.
4. 첫 4쪽을 읽고 세 가지 행동 중 하나를 고르면 결말 4쪽으로 이어진다.
5. 8쪽 글과 삽화 8장을 확인한다. 누락된 삽화는 기존 글과 이미지를 보존하며 다시 요청할 수 있다.
6. 책장을 떠났다가 돌아와도 내용·선택한 결말·그림이 유지된다.
7. 예전 동화는 보관함에서 원문 그대로 읽고, 새 그림책과 혼동하지 않는다.

원고 검수에 실패한 글은 저장하지 않는다. 실패율과 재시도 성공률은 베타 점검 항목이다. 한 번의 성공을 모든 입력에 대한 품질 보증으로 취급하지 않는다.

새 실패 로그 `picturebook_generation_failed`는 시작·결말 단계와 모델 연결·시간 초과·응답 형식 등 고정된 분류만 남긴다. 원고·입력·공급자 오류 본문은 기록하지 않는다. 이미 처리된 `GenerationError`는 이 로그를 남기지 않으므로, 이 로그 건수만으로 전체 품질 거절률이나 사용자 재시도 성공률을 계산하지 않는다.

## 테스트 데이터

새 운영 QA 계정에는 `hodam_test_user: true`와 용도를 표시하고 가상의 아이 정보를 사용한다. 테스트용 원고·빈 기록도 해당 계정에만 만든다. 실제 사용자 기록은 QA 목적으로 변환하거나 삭제하지 않는다.

OAuth 제공자의 신규 가입, 앱의 첫 계정 초기화, 원고 생성, 결말 생성, 삽화 생성, 재방문 검증은 각각 기록한다. 관리자 API로 준비한 테스트 계정의 로그인 검증을 Google·카카오 신규 가입 완료로 기록하지 않는다.

### 의존성 점검

- 배포 전 검사에서 발견한 `brace-expansion`, `fast-uri`, `source-map-js` 경고는 호환 패치 버전으로 업데이트했다. Sass는 1.105.1로 올려 오래된 Chokidar·braces 경로를 제거했다.
- `sass`와 `next-sitemap`은 SCSS 컴파일과 `postbuild` 사이트맵 생성에만 사용하므로 개발 의존성으로 분류했다. CI·Vercel 빌드 단계에서는 개발 의존성까지 설치해야 한다. `npm run check:audit:prod` 결과는 경고 0개다.
- 개발 도구를 포함한 전체 `npm audit`에는 18개 경고(높음 16개, 보통 2개)가 남아 있다. 이 숫자는 두 원인 패키지와 그 상위 의존성 경고를 합친 수다. [braces의 중첩 패턴 재귀 문제](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)는 수정 버전이 아직 없고, [PostCSS 선택자 파싱 문제](https://github.com/advisories/GHSA-rj75-hqrm-r3gf)는 Tailwind 3의 하위 의존성에 남는다. 현재 사용 경로는 저장소에 정의한 파일 패턴·CSS를 처리하는 빌드·린트 도구이며 서비스 이용자의 입력을 이 파서에 넘기지 않는다. 전체 검사가 통과했다고 기록하지 않는다.
- 해결되지 않은 도구 경고는 상위 패키지의 호환 수정판 또는 별도 Tailwind·린트 도구 업그레이드에서 재검토한다. 전체 검사 결과는 `reports/local/mobile-qa-2026-10-06/dependency-audit.json`에 저장한다.

### 운영 로그인 후 복귀 보완

0.2.3 배포 확인 중 운영 Google 기존 계정으로 책 상세에서 로그인을 시작했을 때, 인증 응답이 `/auth/callback` 대신 홈의 `?code=...`로 도착하는 경우를 확인했다. SDK가 로그인과 코드 제거를 완료하지만 홈에는 저장된 복귀 경로를 처리하는 로직이 없어 원래 책으로 돌아가지 않았다.

0.2.4는 홈의 GET 요청에 인증 코드 또는 오류 응답이 있는 경우 같은 출처의 `/auth/callback`으로 307 이동한다. 쿼리를 보존하고 SDK 초기화 전에 기존 콜백 처리로 연결한다. 일반 홈·다른 경로·POST 요청은 그대로 두며, `next` 값으로 목적지를 변경하지 않는다. 기존 콜백의 세션 검증·안전한 복귀 경로 처리·오류 안내를 재사용한다. API의 요청 ID 전달도 유지한다.

추가 회귀 테스트 13개를 포함한 중간 검증에서 전체 191개 파일·1,276개 테스트, 프로덕션 빌드와 변경 파일 린트가 통과했다. 독립 코드 검토에서 추가 결함은 없었다.

실제 로컬 HTTP 검사에서 루트의 `middleware.ts`가 `src/app` 구조에서는 빌드에 포함되지 않는 것을 확인했다(`middleware-manifest.json`이 비어 있음). 파일을 앱과 같은 레벨인 `src/middleware.ts`로 옮겼다. 최종 빌드에서 미들웨어 등록과 코드·오류 응답의 실제 307 이동, 일반 홈 200, 비인증 API 401 및 요청 ID 전달을 검증했다. 함수 단위 테스트만으로 배포 경로 검증을 대신하지 않는다.

미리보기 배포에서 로그인 취소 오류가 일반 실패로 분류되고, 실패 제목 아래에 진행 중 문구가 남는 문제도 재현했다. 제공자의 오류 코드와 설명을 별도로 보존하고, 이미 실패·성공한 화면에서는 진행 문구를 갱신하지 않도록 수정했다. 취소·잘못된 요청·설명 기반 만료 분류와 재시도 경로, 정상 코드 교환 후 원래 책 복귀를 실제 컨트롤러 회귀 테스트로 확인한다.

오류 안내 보완 후 최종 전체 검증은 192개 파일·1,283개 테스트 및 프로덕션 빌드 통과다. 생성기·결제·기존 책 데이터는 변경하지 않았다.

## 2026-10-06 신규 계정·첫 그림책·재시도 QA

운영 기준선은 0.2.4다. 아래 복구·진단 수정은 PR #107의 0.2.5로 배포했다. 앞의 로그인 QA와 달리 이번에는 표시된 별도 합성 QA 계정으로 실제 첫 원고 생성을 시도했다. 관리자 API로 준비한 계정이므로 Google·카카오 제공자 신규 가입 검증은 아니다.

### 실제 운영에서 확인한 결과

- 로그인 전 입력한 가상의 아이 정보와 경험이 인증 후 복원됐고, 첫 계정의 초기 곶감 10개와 빈 책장을 확인했다.
- 기존 코드에서 요청 ID를 페이지 상태에만 보관해 재마운트 시 잃는 문제를 소스와 재마운트 회귀 테스트로 확인했다. 운영 생성 중 시도한 새로고침은 페이지 이탈 경고로 취소됐을 수 있어 실제 전체 새로고침 재현으로 기록하지 않는다. 저장 결과를 모른 채 새 ID로 요청하면 별도 책과 추가 차감으로 이어질 수 있는 경로지만, 이번 실제 시도에서 중복 책이나 중복 차감이 발생한 것은 아니다.
- 실제 첫 원고 생성 2회는 모두 공급자 설정 계열 오류로 실패했다. 저장된 책은 0권, 곶감 차감은 0개였다. 운영 원본 로그는 `category: model_or_response`까지만 남아 있어 정확한 HTTP 상태를 확정하지 못했다. 사용자 안내는 인증·권한 오류(401/403)에 해당했고, 별도로 로컬의 기존 API 키로 모델 목록을 조회한 요청은 `401 invalid_api_key`를 반환했다. 로컬 결과만으로 운영 키의 상태를 단정하지 않는다.
- 운영 Vercel의 `OPEN_AI_API_KEY` 갱신을 사용자에게 요청한 상태다. 공급자 연결이 복구되기 전에는 이번 버전의 신규 8쪽 원고·삽화 8장 완결, 실제 성공 차감과 재방문 검증을 완료로 기록하지 않는다. 9월의 성공 기록으로 이번 검증을 대신하지 않는다.

### 수정 브랜치의 복구 동작과 검증 범위

- 첫 원고 요청의 ID와 입력을 계정별 `sessionStorage`에 보관한다. 같은 탭에서 페이지를 다시 열거나 새로고침하면 보관한 요청을 복원하고, `이전 요청 이어서 확인하기`는 같은 ID로 저장 결과를 확인한다.
- 서버에서 원요청 조회가 실패하면 다음 확인에도 같은 요청 ID를 유지한다. INSERT가 경합·응답 유실로 실패한 경우에는 원래 ID로 저장 결과를 다시 조회한다. 저장 여부가 불분명한 실패를 곧바로 새 요청으로 바꾸지 않는다.
- 미확인 요청이 있다는 이유로 새 책 작성을 계속 막지 않는다. `새 그림책 따로 만들기`를 누르면 이전 요청의 지연 저장 가능성과 별도 곶감 사용을 안내하고, 사용자가 명시적으로 확인한 뒤 새 작성을 시작한다. 이전 ID와 입력은 미확인 목록에 남겨 다시 확인할 수 있게 한다.
- 공급자 오류 진단에서 인증 실패(401), 권한 문제(403), 요청 제한(429), 할당량 부족을 구분하도록 보완한다. 비밀키·입력·원고·공급자 오류 본문을 로그에 남기지 않는다.
- 모의 회귀로 실패·중복 요청·복구 및 명시적 별도 작성 경로를 검증했다. 최종 전체 테스트 195개 파일·1,326개, 프로덕션 빌드(타입 검사·린트 포함), 격리 로컬 DB 회계·소유권 검사가 통과했다. 모의 성공은 운영 원고·삽화 생성 성공을 의미하지 않는다.
- 수정 후 로컬 브라우저에서는 10초 뒤 401을 반환하는 공급자 모의 응답으로 요청을 시작했다. 진행 중 앱 내부 링크로 내 책장에 갔다가 그림책 만들기로 재진입해 복구 안내를 확인했고, 복구 대기 상태에서 전체 새로고침해도 보관된 요청이 유지됐다. 이어서 미확인 목록 보관·새 입력 폼 열기·원래 요청 다시 선택·재시도 후 오류까지 진행하며 복구 정보가 유지되는 것을 확인했다. 이는 실제 브라우저 이동·새로고침 검증이며, 실제 공급자 성공이나 생성 중 강제 새로고침 성공을 뜻하지 않는다.

복구 정보는 계정별로 분리되지만 현재 탭의 `sessionStorage` 수명에 한정된다. 다른 탭·기기와 공유하거나 탭을 닫은 뒤의 복구를 보장하지 않는다. 저장소를 사용할 수 없을 때에는 현재 페이지 상태만 유지하므로 새로고침 복구도 보장하지 않는다.

이번 수정에는 새 원자적 DB 마이그레이션이 없다. INSERT 응답이 유실되거나 곶감 사용 후 작업 프로세스가 종료되어 예약 행만 남은 경우, 같은 ID 재조회만으로 원고를 자동 완성하지 못한다. 이런 미확인 요청은 문의하거나 안내를 확인한 뒤 별도 책을 작성해야 한다. 실제 중단 지점별 회계 복구를 모두 해결했다고 기록하지 않는다.
